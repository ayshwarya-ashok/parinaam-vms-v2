# Runbook — Deploy

Two deployment shapes exist. **Local / fresh machine** is the laptop recipe. **The
Parinaam VM** (`volunteer@164.52.223.64`) runs v2 **alongside v1 for A/B testing** —
v1 keeps serving `volunteer.parinaam.ai` untouched; v2 answers at `vms.parinaam.ai`.

## The Parinaam VM (A/B alongside v1) — deployed 2026-09-17

The topology, in one picture:

```
internet ──443──▶ host Caddy (systemd, /etc/caddy/Caddyfile)
                    ├─ volunteer.parinaam.ai  → v1 (untouched)
                    └─ vms.parinaam.ai        → 127.0.0.1:8090   ← the ONE new line
                                                  │
                                     v2's own Caddy container (pvms-caddy)
                                     ├─ /api/*      → api:3000
                                     ├─ /mailpit/*  → mailpit:8025
                                     └─ /*          → web:5173
```

- **Code** lives at `/opt/parinaam-vms-v2`, checked out from a git *bundle* streamed
  over ssh (`git bundle create vms-v2.bundle feature/ayshwarya`, then
  `cat … | ssh … 'cat > vms-v2.bundle'` — the VM's sshd has no scp binary, and no
  GitHub credentials ever land on the server).
- **`.env`** is generated by `vm-setup.sh` (staged in `/home/volunteer/`): fresh
  `openssl rand -hex 32` secrets, `SEED_DEMO_DATA=true`, and — the important part —
  **every published port is loopback-bound and shifted off v1/shared-infra ports**
  (`POSTGRES_PORT=127.0.0.1:5433`, `REDIS_PORT=127.0.0.1:6380`, front door
  `CADDY_PORT=127.0.0.1:8090`, the rest as below). Nothing of v2 is reachable from
  the internet except through the host Caddy.
- **Email stays in Mailpit** during A/B (`https://vms.parinaam.ai/mailpit/`) — no real
  volunteer can be emailed by accident. Real SMTP later = one n8n credential swap.
- **Going public** (once the `vms.parinaam.ai` A record → 164.52.223.64, DNS-only/gray
  cloud, exists): run `/home/volunteer/vm-go-public.sh` on the VM. It refuses to run
  until DNS resolves, backs up `/etc/caddy/Caddyfile`, appends the site block,
  **`caddy validate` before `systemctl reload caddy`** (a typo must never take down
  v1), then smoke-tests both hostnames.
- **Interim public hostname (live since 2026-09-17)**: `https://parinaam-vms.duckdns.org` —
  a free DuckDNS record pointing at the VM, served by the SAME host-Caddy site-block
  pattern as the future `vms.parinaam.ai` (automatic Let's Encrypt cert). `PUBLIC_WEB_URL`
  and `PUBLIC_API_URL` point at it until the real record lands; the cutover is: run
  `vm-go-public.sh`, flip both env vars, recreate api+worker, optionally remove the
  DuckDNS block.
- **Reaching the stack before DNS** (or the loopback-only surfaces after):
  `ssh -i vm-ssh-key -L 18090:127.0.0.1:8090 volunteer@164.52.223.64`, then open
  `http://localhost:18090`. Same trick for n8n (5679), Adminer (8082), Postgres (5433).
- **Rollback**: remove the `vms.parinaam.ai` block from the host Caddyfile (reload), and
  `docker compose --profile app down` in `/opt/parinaam-vms-v2`. `down -v` also deletes
  the data. v1 never notices either way.
- **Gotchas found on first boot (2026-09-17):**
  1. *Thin seed data* (16 volunteers, no coordinators) meant the seed phase DIED midway —
     the culprit was S002's all-NULL `slides` VALUES column typing as text (fixed with a
     cast in the seed; every fresh clone since Round 1 would have hit it). If counts look
     thin, read `docker logs pvms-db | grep -iB2 error` before blaming timing.
  2. *Services stuck in `Created`*: the first boot's init (migrations + bcrypt-heavy
     seeds) outlasts the db healthcheck window on the VM's CPU, so late dependents give
     up while the db finishes initializing. Once `docker compose ps` shows db healthy,
     a plain `docker compose --profile app up -d` starts the stragglers. A truly broken
     init is instead cured by a clean re-init: `down -v && up -d` (images are cached).

### VM upgrade (subsequent deploys)

```sh
# on the laptop
git bundle create vms-v2.bundle feature/ayshwarya
cat vms-v2.bundle | ssh -i vm-ssh-key volunteer@164.52.223.64 'cat > vms-v2.bundle'
# on the VM
cd /opt/parinaam-vms-v2
git fetch /home/volunteer/vms-v2.bundle feature/ayshwarya && git reset --hard FETCH_HEAD
docker compose exec -T db psql -U parinaam -d parinaam_vms -v ON_ERROR_STOP=1 \
  -f /database/migrations/V0XX__*.sql        # any NEW migrations, then the
                                             # schema_migrations row (see database/README)
docker compose --profile app up -d --build api worker web
```

## Local / fresh machine

```sh
cp .env.example .env          # then change every *_SECRET and password
docker compose --profile app up -d --build
```
First boot applies `database/migrations/V001..` and (if `SEED_DEMO_DATA=true`) the
seeds. Import the n8n workflow once:
```sh
docker compose exec n8n n8n import:credentials --input=/workflows/vms-smtp.credentials.json
docker compose exec n8n n8n import:workflow --input=/workflows/vms-email-dispatch.json
docker compose exec n8n n8n publish:workflow --id=vmsEmailDispatch1
```
Then materialise the seeded training documents (renders a real PDF for every
seed material so "Open" works):
```sh
docker compose cp scripts/generate-seed-materials.mjs api:/app/gen.mjs
MSYS_NO_PATHCONV=1 docker compose exec -T api sh -c "node /app/gen.mjs && rm /app/gen.mjs"
```

## Post-deploy checks (2 minutes — either environment)

```sh
curl -s localhost:3001/api/v1/health/ready        # db + redis + n8n all "up"
node scripts/n8n-drift-check.mjs                  # live workflow matches repo
docker compose exec -T api node scripts/authz-matrix.mjs http://localhost:3000/api/v1
                                                  # 81 endpoints × 4 roles = 324 checks
curl -s -X POST localhost:3001/api/v1/internal/test-email \
  -H "Content-Type: application/json" -d '{"to":"deploy.check@example.com"}'
# → message must appear in Mailpit (locally http://localhost:8026/mailpit/) within ~15 s
```

## Ports (chosen to never collide with v1 / the shared infra)

Front door (Caddy) **8090** · API 3001 · Web 5174 · n8n 5679 · Mailpit UI 8026 /
SMTP 1026 · Adminer 8082 · Postgres 5433 (VM) or 5432 (local) · Redis 6380 (VM) or
6379 (local). On the VM every one of these is bound to `127.0.0.1`.
